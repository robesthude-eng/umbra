# Umbra 0.16.18 — облачное шифрование хранения

Обычный вход по коду сохраняется. Сервер отдаёт историю авторизованным устройствам,
поэтому пользователям не нужно переносить ключ переписки или помнить код восстановления.
Это **облачная модель с ключами сервера, без E2EE**: работающий сервер может прочитать
сообщения и файлы. Она не копирует протокол или инфраструктуру Telegram.

## Что защищено

- Содержимое сообщений в PostgreSQL и дайджесты запросов для защиты от повторной отправки.
- Байты вложений: фото, видео, документы, голосовые сообщения и аватары; как на диске,
  так и в S3/MinIO. Размеры и квоты считаются по исходным байтам.
- Новые записи шифруются до сохранения. Старые — после команды `migrate`.
- Ключи находятся в отдельном файле с правами `0600`/`0400`, а не в базе или APK.
  В базе сохраняются только их публичные идентификаторы. Без файла ключей сервер
  не запускается; неполный или посторонний набор ключей также отклоняется.

Шифрование защищает содержимое при утечке отдельно взятой базы или хранилища файлов.
Доступ к работающему серверу и ключам позволяет расшифровку. Телефоны, профили,
названия групп, участники, адресация, размеры файлов и время событий остаются
метаданными в базе. Сетевая защита требует HTTPS/WSS. Локальная история Room и
медиакэш Android этим обновлением не шифруются. Защита звонков остаётся на уровне WebRTC.

## Формат и ключи

Записи используют AES-256-GCM со случайным 96-битным nonce из стандартной библиотеки Go
(`cipher.NewGCMWithRandomNonce`). Версия, идентификатор ключа и контекст записи
аутентифицируются. Контекст сообщения включает ID, отправителя, адресата и чат;
перестановка зашифрованных записей обнаруживается. Для квитанций используется
отдельный контекст. Открытые SHA-256 дайджесты тоже переносятся в зашифрованный вид,
чтобы по утекшей базе нельзя было подбирать короткие сообщения через их хэши.

У каждого файла собственный случайный 256-битный ключ. Он защищён серверным ключом
и привязан к публичному ID файла; содержимое обрабатывает потоковый формат DARE v2
из `github.com/minio/sio v0.5.1` с AES-GCM. Память не растёт пропорционально размеру
вложения. Дополнительный аутентифицируемый байт обеспечивает проверку пустых файлов.
При скачивании последний байт удерживается до проверки завершения потока, чтобы
повреждённый ответ не выглядел для клиента успешно скачанным.

Ссылки на используемые реализации: [Go cipher](https://pkg.go.dev/crypto/cipher#NewGCMWithRandomNonce),
[MinIO sio](https://github.com/minio/sio). Это реализация на стандартных библиотеках,
а не заявление о пройденном независимом криптографическом аудите.

**Сохраните отдельную резервную копию файла ключей до начала записи данных.**
Потерянный ключ нельзя восстановить из базы. Не кладите ключ в тот же общедоступный
архив, что базу и вложения, не добавляйте его в Git и Docker-образ. Каталог `keydata`
в Compose отделён от `pgdata` и `blobdata`, но все эти тома всё равно доступны
администратору хоста.

## Новый сервер: Docker Compose

Из корня исходников:

```bash
cp .env.example .env
# Заполните POSTGRES_PASSWORD, настройки Telegram, TURN_SECRET и TURN_PUBLIC_IP.
docker compose build server
docker compose create --no-deps server
docker compose run --rm --no-deps --entrypoint /umbra-storage server init
umask 077
mkdir -p backups
docker compose cp server:/data/keys/storage-keys.json ./backups/storage-keys.json
chmod 600 ./backups/storage-keys.json
# Сохраните эту копию ключей отдельно от хоста и данных.
docker compose up -d
```

В существующем Compose переменные `TURN_SECRET` и `TURN_PUBLIC_IP` обязательны
при разборе конфигурации, даже когда профиль `turn` не запускается. Укажите
случайный секрет TURN и внешний IP сервера в `.env`. Сам coturn запускается
отдельно по `docs/deploy.md`.

Новая база получает миграции `001`–`016` автоматически. `init` выполняется **один раз**:
существующий файл не перезаписывается. При повторном запуске сервера используйте
тот же том `keydata`; не создавайте новые ключи вместо потерянных.
Команда `docker compose down -v` удаляет постоянные тома, включая ключи.

## Обновление работающего сервера с 0.16.16

Сначала сделайте согласованную резервную копию базы и файлов. Остановите все экземпляры
Umbra и фоновые задания GC/backup на время переноса. Сохраняйте существующие тома.
На большой медиатеке нужны дополнительное место и время: старая копия остаётся
до проверки новой и фиксации указателя в базе. Для простого планирования предусмотрите
место под вторую копию всей медиатеки плюс небольшой служебный запас.

```bash
docker compose stop server
docker compose up -d db
# Для базы 0.16.16, где миграции до 014 уже применены:
docker compose exec -T db sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -v ON_ERROR_STOP=1' < migrations/015_cloud_storage.sql
docker compose exec -T db sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -v ON_ERROR_STOP=1' < migrations/016_account_security.sql
docker compose build server
docker compose create --no-deps server
docker compose run --rm --no-deps --entrypoint /umbra-storage server init
umask 077
mkdir -p backups
docker compose cp server:/data/keys/storage-keys.json ./backups/storage-keys.json
chmod 600 ./backups/storage-keys.json
# Сохраните ключи отдельно, затем перенесите данные:
docker compose run --rm --no-deps --entrypoint /umbra-storage server migrate
docker compose run --rm --no-deps --entrypoint /umbra-storage server status
docker compose up -d server
```

Ожидаемый результат `status` после переноса:

```json
{"legacy_messages":0,"legacy_media":0,"legacy_receipts":0}
```

Если ключи уже созданы, пропустите `init`: повторная генерация не нужна. На базе
старше 0.16.16 сначала примените только недостающие миграции до `014` по порядку.
Не запускайте `011` повторно: она отзывает сессии. Автоматического журнала применения
миграций в проекте нет, поэтому факт обновления фиксирует администратор.

`migrate` переносит сообщения транзакционными пакетами. Для каждого старого файла
создаёт отдельный зашифрованный объект, полностью расшифровывает его обратно и
проверяет SHA-256 и размер; лишь затем атомарно меняет физический указатель.
Публичный ID, URL, права доступа и квота не меняются. Старый объект попадает в
устойчивую очередь удаления. В конце успешного переноса очередь очищается.

При ошибке команда завершается с ненулевым кодом. Устраните причину и повторите
`migrate` с тем же файлом ключей: уже перенесённые записи пропускаются. При потере
ответа на COMMIT новая копия не удаляется, поскольку транзакция могла завершиться.
Невостребованные копии может убрать `cmd/gc` после защитного интервала 24 часа.
`status` показывает остаток старых записей, но не проверяет все ключи и содержимое
всех файлов; это не полный тест восстановления резервной копии.

Новый сервер умеет читать старые записи до переноса, однако они остаются открытыми
в хранилище. После появления зашифрованных записей запуск сервера 0.16.16 напрямую
на этих данных не поддерживается. Для отката нужна согласованная копия базы и
файлов, сделанная до обновления. Прежние дампы, WAL, снимки диска и версии объектов
S3 не становятся зашифрованными задним числом; управляйте их сроком хранения отдельно.

## Прямой запуск и systemd

`make build` собирает `bin/server` и `bin/umbra-storage`; оба бинарника также
включены в workflow `server-binary.yml`. Скопируйте их в `/usr/local/bin/` как
`umbra-server` и `umbra-storage`. Для примера `deploy/umbra.service` файл ключей:

```bash
sudo install -d -o deploy -g deploy -m 700 /opt/umbra/data
sudo -u deploy /usr/local/bin/umbra-storage init -key-file /opt/umbra/data/storage-keys.json
```

Сохраните копию ключей отдельно. Для CLI задайте то же окружение, что у сервиса:
`STORE=postgres`, `DATABASE_URL`, `BLOB_DIR` или параметры S3, `STORAGE_KEY_FILE`.
CLI **не читает `.env`/`umbra.env` автоматически**. Остановите сервис, примените SQL
через `psql -v ON_ERROR_STOP=1`, выполните `umbra-storage migrate` и `status`
от пользователя `deploy` с этим окружением, затем перезапустите сервис.

Для локальной разработки: `make storage-init`, затем `STORE=memory make run`.
MemoryStore не сохраняет сообщения между запусками; для семейной переписки нужен PostgreSQL.

## Ротация

```bash
umbra-storage rotate -key-file /secure/storage-keys.json -out /secure/storage-keys-next.json
```

Команда создаёт новый активный ключ и сохраняет **все старые**. Выходной файл не должен
существовать. Сделайте его отдельную резервную копию, замените `STORAGE_KEY_FILE`
в конфигурации и перезапустите сервер. В Docker создавайте файл внутри постоянного
тома ключей и меняйте путь в Compose. Не удаляйте предыдущие ключи из JSON:
история, вложения и старые резервные копии могут от них зависеть.

Новые записи используют новый ключ; старые автоматически не перешифровываются.
`migrate` обрабатывает только формат 0, а не повторно шифрует формат 1.
Для GCM со случайным nonce нельзя достигать 2³² шифрований одним ключом:
меняйте ключ заранее; в счёт входят сообщения, квитанции и ключи файлов/бэкапов.
При компрометации старого ключа эта ротация сама по себе не закрывает доступ
к уже полученным злоумышленником данным.

## Зашифрованные резервные копии

В 0.16.18 `deploy/umbra-backup.sh` шифрует весь дамп автоматически, включая
метаданные. Настройка юнита и PGPASSFILE — SECURITY.md. Ручной вариант при
настроенных PGHOST/PGPORT/PGUSER/PGDATABASE и защищённом PGPASSFILE:

```bash
set -euo pipefail
umask 077
pg_dump --no-password -Fc | umbra-storage encrypt-backup > database.dump.umbraenc.part
mv database.dump.umbraenc.part database.dump.umbraenc
```

`STORAGE_KEY_FILE` должен указывать на действующий набор ключей. Для восстановления
сначала полностью проверьте расшифровку во временный файл, и только после успеха
передавайте дамп в `pg_restore`:

```bash
set -euo pipefail
umask 077
umbra-storage decrypt-backup < database.dump.umbraenc > database.dump.part
mv database.dump.part database.dump
# Теперь можно восстанавливать database.dump в выбранную базу.
```

Не направляйте непроверенную расшифровку сразу в `pg_restore`: при повреждении конца
потока команда может успеть вывести начальные байты, а затем вернуть ошибку.
Удаляйте незавершённый `.part` после ошибки. Вложения, база и ключи резервируются
отдельно; для согласованного снимка остановите запись на время копирования.
Проверяйте восстановление на отдельной базе и копии медиатеки.

При переходе с 0.16.17 сохраните существующие ключи и примените миграцию 016
перед запуском нового сервера. Повторный init не нужен; следуйте SECURITY.md.
