# Umbra 0.16.16 — медиа по области видимости и честные звонки (12 сентября 2026)

Безопасность и исправление звонков; детали — FIXES_0.16.16.md.

- `GET /v1/media/{id}` больше не отдаёт файл любому авторизованному пользователю:
  доступ имеют владелец, адресат личного чата, участники группы и все — пока
  файл является чьим-то текущим аватаром; посторонним — 404.
- Загрузка принимает `chat_id`/`recipient_id` (взаимоисключающие) с проверкой
  членства; миграция `migrations/014_media_scope.sql`; откат старого поведения —
  `MEDIA_LEGACY_OPEN_ACCESS=1` для файлов без области видимости.
- Клиент передаёт область видимости при загрузке вложений; пересылка вложений
  перезагружает файл (старый id в новом чате недоступен по правилам доступа).
- Звонки: повторный вызов занятому адресату — 409, сигналы — только для
  ringing/active, терминальные статусы защищены (идемпотентный повтор — 200,
  смена — 409).
- Подвисшие вызовы: maintenance переводит ringing старше 90 секунд в missed
  (`ExpireRingingCalls`, memory + postgres).
- Тесты: `TestMediaAccessControl`, обновлённые `TestMediaRoundTrip` и
  `TestMediaStorageFailures`; обновлён `docs/api.md`.
- Версия Android: versionCode 39, versionName 0.16.16.

# Umbra 0.16.6 — время с зоны сервера и независимая отправка (11 сентября 2026)

Причина инцидента «test-устройство принимает, но не отправляет» найдена по
журналу диагностики: сервер, перезапущенный 10 сентября в 20:44 в зоне
Europe/Moscow, стал отдавать метки времени из базы со смещением «+03:00»
(например «2026-09-10T21:17:47.307663+03:00»). Instant.parse на Android
понимает только суффикс «Z» — синхронизация падала на первом же сообщении,
а вместе с ней и отправка: очередь флашится только после успешной загрузки
истории. Телефон при этом продолжал принимать сообщения через живой
WebSocket, поэтому сбой выглядел как «только отправка сломана».

- Новый tolerant-парсер `data/repo/IsoTime.kt`: метки и с «Z», и со
  смещением зоны («+03:00») разбираются одинаково (`Instant.parse` →
  `OffsetDateTime.parse`).
- Отправка больше не зависит от приёма: `refresh()` флашит очередь даже
  когда синхронизация упала — сообщения не висят «часиками» до ручного
  действия (ChatRepository.refresh, pollJob).
- Ошибка тихой синхронизации при живом WebSocket фиксируется в журнале
  диагностики (тег poll-sync) и честно показывается статусом, а не
  проглатывается.
- Зависшие при обрыве/обновлении приложения сообщения теперь уходят сами
  при первом же цикле опроса.
- Версия Android: versionCode 29, versionName 0.16.6.

# Umbra 0.16.5 — надёжная отправка и диагностика (11 сентября 2026)

Починка по инциденту «второе устройство принимает, но не отправляет»
(очередь отправки зависала до HTTP-запроса; прямой канал WebSocket на
мобильных сетях рвётся каждые 8–190 секунд).

- Мьютекс отправки берётся с таймаутом 30 с: зависшая попытка больше не
  блокирует все последующие (`ChatRepository.flushOutbox`).
- После 5 неудачных попыток сообщение помечается ошибкой с настоящей
  причиной (`IllegalStateException`, `IOException` и т.п.) вместо вечных
  «часиков»; очередь продолжает отправку остальных сообщений.
- Журнал диагностики `data/diag/DiagLog.kt`: технические события без
  содержимого сообщений; кнопка «Настройки → Диагностика → Отправить журнал».
- Переподключение WebSocket теперь запускает инкрементальную синхронизацию,
  а не полную (минус лишний трафик на нестабильных сетях).
- Честный статус: «Медленный режим» вместо пугающего «Подключение…», когда
  прямое соединение прервано, но опрос каждые 5 секунд работает.
- Смена сессии внутри обработки событий больше не показывается как ошибка.
- Версия Android: versionCode 28, versionName 0.16.5.

# Umbra — 8 сентября 2026 (третья итерация): v0.4 (в работе) — вход по номеру с кодом из Telegram, модель «как в Telegram»

Решение пользователя: приложение для семьи; подтверждение номера кодом, который
приходит в Telegram-бот; один аккаунт на номер; вход с любого телефона по номеру
и коду подтягивает переписку, файлы и профиль из облака (T1, как обычные чаты
Telegram). Старые E2EE-аккаунты удалены (переход на новую модель).

## Сервер (готово)

- Миграция `009_otp_telegram.sql`: таблица привязки `tg_bindings` (номер ↔ чат
  бота для доставки кодов) и `user_profiles` (аватар).
- `POST /v1/auth/request_code {phone}` — генерирует 6-значный код (TTL 5 мин,
  в памяти сервера), отправляет его в привязанный Telegram-чат. Без привязки —
  понятная ошибка. Rate-limit 6/мин на IP.
- `POST /v1/auth/verify_code {phone, code}` — если аккаунт с номером есть: вход
  (выдаёт сессионный токен); если нет: регистрирует облачный аккаунт
  (username `u<цифры>`, dummy Signal-ключи — в этой модели не используются).
  Возвращает `new_account` и `profile_complete`. Один аккаунт на номер; код
  одноразовый, до 5 попыток.
- `POST /v1/account/profile {username?, name?}` (auth) — завершение регистрации:
  @username (уникальный, опционально) и имя (обязательно для нового аккаунта).
  409 при занятом username.
- `POST /v1/account/avatar {media_id}` (auth) — фото профиля (медиа загружается
  через существующий `POST /v1/media`, проверяется владелец). `GET /v1/account`
  теперь возвращает `avatar_media_id`.
- Облачная история: `GET /v1/messages` возвращает и входящие, и собственные
  исходящие DM — на новом телефоне после входа подтягивается вся переписка.
- Telegram-клиент (`internal/telegram`): long-polling getUpdates — бот принимает
  от членов семьи номер телефона и привязывает его к чату (один слушатель на бота:
  n8n/другие опросы того же бота конфликтуют и должны быть отключены).
- Доставка включается env `TELEGRAM_BOT_TOKEN`. Без токена request_code → 503.
- Тесты: handler-тесты OTP (регистрация/вход/ошибки/занятый username) +
  интеграционные (PostgreSQL: миграции 001–009, привязка, профиль, аватар).

## Android (в работе)

- Экран регистрации: номер → код из Telegram → @никнейм → имя → фото профиля.
- Вход по номеру: код → загрузка профиля, переписок и файлов с сервера.
- Переписка в облачном режиме (без E2EE-конвертов Signal).

# Исправления Umbra — 7 сентября 2026

Обновлены сервер и Android-клиент. Это исходный проект, без собранного APK
или серверного бинарника. Основные версии зависимостей сохранены.
Android versionName=0.2.0, versionCode=2, Room schema=2.

## Сервер

- Ed25519 auth принимает raw и прежний X.509 DER. Новые записи нормализуются,

- общий контракт memory/PostgreSQL: конкурентная квота, конкурентные повторы,
  повтор после очистки сообщения, равные временные метки, удаление участника/владельца;
- повтор удаления файла после недоступности хранилища, GC dry-run и отказ при ошибке
  БД, сохранение недавней загрузки; отдельная S3-проверка;
- Android: реальный libsignal между двумя профилями, перезапуск ratchet, откат
  decrypt/pre-key, сохранение identity/pending-пакета, блокирование подмены;
- Android: миграция Room и восстановление очереди после принятого сообщения
  с потерянным HTTP-подтверждением, направление входящего DM и ответ собеседника.

Команды запуска находятся в README.md и android/README.md. PostgreSQL-тесту нужна
отдельная TEST_DATABASE_URL; S3-тест использует переменные TEST_S3_*.

## Порядок обновления

1. Сделайте согласованную резервную копию БД и файлов.
2. Остановите старый сервер и примените недостающие миграции по порядку. Если
   схема уже 001–005, примените migrations/006_integrity.sql.
3. Запустите новый сервер. Обновите оба Android-клиента тем же ключом подписи,
   сохранив данные приложения. Подробные ком��нды — docs/deploy.md.

Миграция PostgreSQL сохраняет прежние orphan rows через NOT VALID; их разбор
описан в инструкции обновления. Ничья действующая БД, аккаунты или файлы во время
подготовки этого архива не очищались.

## Что остаётся ограничением

- Прежний клиент не сохранял часть криптосостояния и исходящий текст. Уже
  утраченные данные нельзя восстановить обновлением; старые ciphertext не удаляются.
- Групповое E2E, медиа, WebRTC, push при остановленном процессе, перенос ключей,
  экран fingerprints и выбор таймера в Android ещё не реализованы.
- Отправка в группы отключена до реализации групповых ключей; клиент не пытается
  выдавать личную Signal-сессию за групповую.
- Первая identity принимается по TOFU. Старые private pre-keys сохраняются для
  сообщений в пути; автоматическая политика их удаления не добавлялась.
- Backend рассчитан на один экземпляр сигналинга. За прокси лимит применяется
  к адресу прокси; распределённые лимиты и межсерверная рассылка не реализованы.
- Удаление серверных/локальных строк не стирает чужие копии, бэкапы, следы SQLite
  или прежние версии объектов S3. Это требует отдельной политики хранения.
