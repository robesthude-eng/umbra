# Umbra 0.16.18 — безопасность и обновление

Клиент: 0.16.18, versionCode 41. Сохранена облачная модель: сервер хранит ключи,
авторизованные устройства получают историю без переноса ключей. Это **не E2EE**
и не копия протокола Telegram. Работающий сервер может прочитать сообщения и
файлы. Формат шифрования хранения — CLOUD_STORAGE.md.

## Обновление с 0.16.17

Сохраните согласованные копии базы, вложений и существующего файла ключей.
**Не запускайте init и не заменяйте ключи новым набором** на существующей истории.
Остановите сервер и задания записи/GC на время обновления. Примените только новую
миграцию `016_account_security.sql`; для Compose, при работающей БД:

```bash
docker compose stop server
docker compose exec -T db sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -v ON_ERROR_STOP=1' < migrations/016_account_security.sql
# Настройте AUTH_ALLOWED_PHONES в .env, затем:
docker compose up -d --build server
curl --fail http://127.0.0.1:8080/healthz
```

Новый сервер проверяет наличие схемы 016 перед запуском. Миграция сохраняет
аккаунты, переписку и действующие токены, добавляет метаданные сессий. Старые
push-привязки удаляются: откройте приложение на каждом телефоне для повторной
регистрации FCM. До открытия фоновые уведомления могут не приходить.

Установите Android с прежним ключом подписи. Старый клиент больше не сможет
удалить аккаунт без отдельного подтверждения. Для версий до 0.16.17 сначала
выполните перенос облачного хранения по CLOUD_STORAGE.md, включая миграцию 015,
затем 016. У новой пустой БД Compose применяет 001–016 автоматически. Не запускайте
все старые миграции повторно: некоторые из них намеренно отзывали токены.

## Разрешённые номера и коды

`AUTH_ALLOWED_PHONES` — номера E.164 через запятую, например
`+79991234567,+79991234568`. Пробелы вокруг элементов допустимы; звёздочки,
пустые элементы и форматирование внутри номера запрещены.

- Пустое значение разрешает вход только в уже существующие телефонные аккаунты.
  Для первых регистраций явно добавьте номера семьи.
- Непустое значение ограничивает вход и действующие HTTP/WS-сессии телефонных
  аккаунтов только перечисленными номерами. Изменение требует перезапуска.
- Оставьте `ALLOW_LEGACY_AUTH=false`. Его явное включение разрешает старую
  аутентификацию ключом аккаунтам без номера; на них список телефонов не действует.
- Исключение номера не удаляет токены: после повторного разрешения неистёкшая сессия
  может снова заработать. Для окончательного отзыва используйте управление сессиями.

Коды поступают владельцу сервера в Telegram. Это подтверждение владельцем,
**не проверка владения SIM-картой**. Защитите его Telegram двухэтапной аутентификацией
и проверяйте запрос перед передачей кода. Бот указывает действие и название
устройства. Название сообщает клиент: это подсказка, а не аппаратное удостоверение.

Код действует 5 минут, хранится как хэш и используется один раз. Пауза между
отправками — 60 секунд; на номер — максимум 5 отправок и 10 неверных проверок
за 30 минут, до 5 ошибок для одного кода. Перевыдача и успешная проверка не
сбрасывают общий бюджет. Лимиты общие для входа и удаления, поверх ограничений IP.
В памяти сохраняется не более 4096 номеров; старые записи очищаются при запросах.
Это состояние одного процесса: перезапуск сбрасывает коды/бюджеты. Для нескольких
экземпляров сервера нужно общее хранилище кодов и лимитов.

Android передаёт device_name и возвращает request_id. Старые запросы без
названия устройства временно совместимы с проверкой без request_id, под теми же
лимитами. Ticket связывает выдачу и проверку, но не является отдельным фактором
или доказательством подлинности устройства.

## Устройства и удаление

«Настройки → Конфиденциальность → Устройства» показывает активные сессии.
Можно отозвать одну другую сессию или все остальные. Их push-привязки удаляются;
WS аккаунта закрывается, оставшиеся сессии переподключаются. Токены и их хэши
список не раскрывает. После входа/refresh срок задаёт TOKEN_TTL_SECONDS, но общая
жизнь сессии ограничена 90 днями. Для старых токенов отсчёт начинается при миграции.
Время «Обновление сессии» отражает вход/refresh, а не каждое чтение сообщения.

Новый вход в существующий аккаунт вызывает уведомление через WS и FCM прежним
устройствам. Доставка зависит от сети и настроек Android. Обязательного одобрения
старым устройством нет — код выдаёт владелец. Отзыв сессии не стирает ранее
скачанные данные и не отменяет уже отправленные уведомления. Новые push содержат
user_id; Android игнорирует уведомления другого или вышедшего аккаунта.

Для удаления нужен отдельный код действия delete_account. Он привязан к запросившей
сессии, действует 5 минут, используется один раз. Код входа или другой сессии
не подходит. Неверный код удаления возвращает 400 и не выбрасывает из аккаунта;
истёкший требует нового запроса. Для старых аккаунтов без номера этот сценарий
недоступен — требуется администратор. Чужие и резервные копии могут сохраниться.

## Резервные копии

deploy/umbra-backup.sh шифрует весь поток pg_dump, включая метаданные.
Готовый umbra_*.umbraenc появляется после успешного дампа и шифрования; обычные
ошибки/сигналы очищают .part. После SIGKILL/аварии .part может остаться, он не
считается готовой копией. Права: файл 0600, каталог 0700. flock предотвращает
параллельный запуск. Копии старше 7 дней удаляются только после нового успешного
бэкапа. Старые открытые .dump не шифруются и не удаляются автоматически.

Новый systemd-юнит работает от deploy вместо postgres, чтобы читать защищённые
ключи. После `make build`, для стандартной структуры:

```bash
sudo install -o root -g deploy -m 0750 deploy/umbra-backup.sh /usr/local/bin/umbra-backup.sh
sudo install -o root -g deploy -m 0750 bin/umbra-storage /usr/local/bin/umbra-storage
sudo install -d -o deploy -g deploy -m 0700 /var/backups/umbra
sudo install -o root -g deploy -m 0640 deploy/backup.env.example /opt/umbra/backup.env
sudo install -m 0644 deploy/umbra-backup.service /etc/systemd/system/umbra-backup.service
sudo install -m 0644 deploy/umbra-backup.timer /etc/systemd/system/umbra-backup.timer
```

Если каталог существовал от postgres, отдельно проверьте владельца/права прежних
копий при переходе. Заполните backup.env под свой сервер и создайте файл
`/opt/umbra/data/backup.pgpass` от deploy с правами 0600. Формат записи:
`hostname:port:database:username:password`; `:` и `\` в пароле экранируются.
Нужна реальная разрешённая учётная запись PostgreSQL. Пароль не передаётся в
аргументах процесса. Не ослабляйте права ключей и не публикуйте пароли/дампы.

```bash
sudo systemctl daemon-reload
sudo systemctl start umbra-backup.service
sudo systemctl status umbra-backup.service
sudo systemctl enable --now umbra-backup.timer
```

Сначала проверьте ручной запуск, затем включайте таймер. Дамп не включает внешние
вложения и ключи: сохраняйте их отдельно и согласованно с БД; ключи — отдельно
от копий. Для восстановления полностью расшифруйте временный дамп и только после
успешного завершения запускайте pg_restore в изолированную БД. Сбой расшифровки
может оставить частичный временный файл — использовать его нельзя.

## Проверки и границы защиты

CI включает Go race, PostgreSQL 16, Android build/Lint, govulncheck, Gitleaks
для файлов и истории; Dependabot проверяет зависимости еженедельно. Фактические
локальные результаты — FIXES_0.16.18.md. Узкое исключение Gitleaks относится
только к ложному совпадению пустого TURN_SECRET со следующей строкой
TURN_TTL_SECONDS в .env.example; реальные значения оно не разрешает.

Рабочий сервер не развёртывался и не проверялся удалённо. Отдельно нужны проверки
SSH, firewall, HTTPS/WSS, обновлений ОС и недоступности портов БД/MinIO извне.
На самом хосте помогают `ss -lntup` и `sshd -T`. Захват сервера вместе с ключами
даёт доступ к данным. Локальные Room и медиакэш Android этим обновлением не
шифруются. Полное восстановление реальной БД/вложений и проверка на телефонах
остаются необходимыми эксплуатационными проверками.

## Инвайт-коды и OTP (v0.19)

- Инвайт-коды выдаёт только владелец (номер из `AUTH_ALLOWED_PHONES`).
  Пустой allow-list отключает выдачу кодов (403).
- В базе хранится только SHA-256 инвайт-кода; сам код показывается один раз.
- История использований хранит `phone_hash`, а не номер.
- OTP-коды хранятся хешем `SHA-256(request_id + ":" + code)`, сравнение —
  за постоянное время; лимиты: 5 отправок и 10 ошибок на 30 минут, кулдаун 60 с.
