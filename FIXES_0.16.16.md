# Исправления 0.16.16

Что поправлено после разбора 0.16.15, почему и что сделать при обновлении.
Порядок — по серьёзности.

---

## 1. Медиа: доступ по области видимости, а не по знанию id

**Было.** `GET /v1/media/{id}` отдавал файл любому пользователю с валидным
токеном. Идентификаторы попадают в конверты сообщений, в логи клиентов и в
резервные копии, поэтому знание одного id открывало чужое фото, видео,
документ или голосовое — без участия в чате. Для мессенджера с заявкой на
приватность это была главная дыра сборки.

**Стало.** У файла появилась область видимости, заданная при загрузке:

- `chat_id` — файл доступен участникам этого чата (группа или канал);
- `recipient_id` — файл доступен владельцу и адресату личной переписки;
- без области — только владельцу, плюс особый случай: если файл установлен
  текущим аватаром, его отдаёт всем (аватары рисуются в списках и профилях).

Посторонний получает `404`, а не `403`: ответ не должен подтверждать, что файл
с таким id вообще существует. Проверка при загрузке: чужой или неизвестный чат
— `403`, неизвестный адресат — `404`, обе области сразу — `400`.

**Файлы.** `internal/model/model.go`, `internal/config/config.go`,
`internal/store/{store.go,postgres.go,postgres_reliability.go}`,
`internal/httpapi/media.go`, `migrations/014_media_scope.sql`,
`internal/httpapi/media_test.go` (новый `TestMediaAccessControl`), `docs/api.md`.

**Клиент.** `UmbraApi.uploadMedia` принимает `chat_id`/`recipient_id`;
`ChatRepository.ensureMediaUploaded` подставляет ту же развилку, что и отправка
конверта (личная переписка — адресат, группа/канал — чат). Аватар грузится без
области видимости.

**Пересылка.** `forwardMessage` раньше переиспользовал готовый media id. С
новыми правилами это означало бы, что в новом чате файл не скачает никто, кроме
отправителя, поэтому вложение перезагружается: файл берётся из локального кэша,
а если его нет — один раз скачивается с сервера. Текст по-прежнему пересылается
без трафика.

## 2. Звонки: занятость и статусный автомат

**Было.** `POST /v1/calls` не смотрел на текущие вызовы: одному человеку можно
было дозвониться десять раз параллельно, и каждый вызов рассылал свои push и
WS-события. Сигналы (`/signal`) принимались и для завершённых вызовов, а
`/status` позволял переводить `ended` → `active`, то есть «оживлять» звонок
после отбоя.

**Стало.**

- перед созданием вызова проверяются звонящие и вызываемые: если у кого-то есть
  свой `ringing` не старше 60 секунд — `409` («already calling» для себя,
  «callee is busy» для собеседника);
- `active` намеренно не считается занятостью: упавший клиент оставляет такой
  статус навсегда, и это заблокировало бы звонки насовсем;
- `/signal` для вызова вне `ringing`/`active` — `409` «call is not active»;
- `/status` из терминального состояния: тот же статус — идемпотентный `200`,
  другой — `409` «call already finished».

**Файлы.** `internal/httpapi/calls.go`.

---

## 3. Подвисшие вызовы больше не висят в «ringing»

**Было.** Если вызываемый не ответил и никто не прислал статус (убили процесс,
пропала сеть), запись оставалась `ringing` вечно: в истории звонков — «идёт
вызов», в списке — вечный звонок.

**Стало.** Фоновое обслуживание раз в 10 секунд помечает `ringing` старше 90
секунд как `missed`.

**Файлы.** `internal/store/{store.go,memory.go,postgres.go}` (новый
`ExpireRingingCalls`), `internal/maintenance/maintenance.go` (`ExpireCalls`).

**Известное ограничение.** Подметённые вызовы не рассылают WS-событие: клиент
увидит `missed` при следующем `GET /v1/calls`. Рассылка из maintenance требует
доступа к хабу — отдельная задача.

## Что сделать при обновлении

1. **Применить миграцию** `migrations/014_media_scope.sql` вручную:

   ```sh
   psql "$DATABASE_URL" -f migrations/014_media_scope.sql
   ```

   Сервер миграции не применяет. `docker-compose.yml` монтирует каталог в
   `docker-entrypoint-initdb.d`, а это работает только на пустой базе.
   Миграция идемпотентна (`ADD COLUMN IF NOT EXISTS`).

2. **Обновлять сервер и клиент вместе.** Клиент 0.16.15 область видимости не
   присылает, поэтому его вложения после обновления сервера открываются только
   владельцу.

3. **Файлы, загруженные до обновления,** области видимости не имеют — они тоже
   останутся доступны только владельцу. Если нужно сохранить прежнее поведение
   на переходный период, поставьте `MEDIA_LEGACY_OPEN_ACCESS=1` и снимите флаг
   после того, как пользователи обновятся. Флаг возвращает старую (небезопасную)
   логику для всех файлов, а не только для старых, — это временный костыль.

## Чего нет в этих правках

- **Сборка и тесты не запускались**: в песочнице нет Go, gofmt, Gradle и сети.
  Перед деплоем прогоните `gofmt -l .`, `go vet ./...`, `go test ./...` и сборку
  Android.
- **Сквозного шифрования по-прежнему нет** ни в группах, ни в личной переписке:
  сервер видит конверты. Область видимости — контроль доступа, а не E2E.
- **Групповые звонки остаются mesh до 4 участников**; SFU не добавлялся.
- Интеграция с Telecom/`ConnectionService`, статусы прочтения и подключение
  уже существующих серверных ручек `typing` к интерфейсу — отдельные задачи.
- Мелочи оформления (застрявший переключатель «Цвета обоев» в темах, где он
  скрыт; отсутствие индикаторов загрузки по категориям настроек) не менялись:
  это косметика, а правки в Compose без компиляции слишком рискованны.
