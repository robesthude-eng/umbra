> Актуализация для Android 0.4.1: клиент использует OTP-вход и облачные JSON-конверты без сквозного шифрования. Старые key/challenge API ниже сохранены на сервере для совместимости. `GET /v1/messages` возвращает `client_message_id`; курсор `since` при пагинации нужно передавать с исходной дробной частью секунды. `GET /v1/account` включает `last_name`, OTP-ответ — `avatar_media_id`. В `POST /v1/account/profile` отсутствующее `last_name` сохраняет фамилию, явная пустая строка удаляет её. Ответ обновления статуса вызова — объект с `status`, а не полный объект вызова.

# API Umbra — контракт эндпоинтов

Серверная часть мессенджера Umbra. Все запросы/ответы — JSON (кроме медиа-блобов и
WebSocket). Бинарные данные в JSON — base64. Аутентификация — Bearer-токен.

Базовый URL: `https://<ваш-домен>` (продакшн) или `http://localhost:8080` (локально).

## Общие положения

### Формат ошибок

Все ошибки возвращаются в виде:

```json
{ "error": "описание" }
```

### Аутентифицированные запросы

Заголовок:

```
Authorization: Bearer <token>
```

Токен выдаётся после `verify_code`, срок — `TOKEN_TTL_SECONDS` (по умолчанию
2592000 секунд, 30 дней после входа/продления). Сервер хранит SHA-256 хэш токена.

## Аутентификация

Текущий Android использует номер телефона и одноразовый код.

### Запрос и проверка кода

`POST /v1/auth/request_code`: JSON с полем `phone`. Код приходит владельцу
Umbra в Telegram; владелец передаёт его пользователю. Это не SMS-проверка
владения SIM-картой. Код действует 5 минут, допускается 5 неверных попыток.

`POST /v1/auth/verify_code`: JSON с полями `phone` и `code`. Возвращает `token`,
`expires_at`, `new_account`, `profile_complete` и `account`. При первом входе
создаётся аккаунт, последующие входы восстанавливают тот же аккаунт.

### Продление сессии

`POST /v1/auth/refresh`, без тела, с `Authorization: Bearer <token>`.
Ответ 200: `{"expires_at":"2026-10-09T12:00:00Z"}` (пример).

Продлевает только действующий токен того же пользователя. Сам токен остаётся
прежним: запрос можно повторить после потери ответа. Истёкший/отозванный токен
возвращает 401; сбой хранилища — 503. Продление и проверка отзыва атомарны.
Android вызывает маршрут при полной синхронизации. Старый сервер с 404/405
обслуживается без продления, до обновления сервера.

`POST /v1/auth/logout` отзывает предъявленный токен; существующий контракт сохранён.

### Совместимость со старым входом по ключу

`POST /v1/register`, `POST /v1/auth/challenge`, `POST /v1/auth/verify` по умолчанию
возвращают 410. `ALLOW_LEGACY_AUTH=true` включает их только для аккаунтов без
номера телефона. В регистрации обязательны username и корректный набор ключей.
Переданный `phone` отклоняется с 403. Уже существующий телефонный аккаунт нельзя
авторизовать по ключу ни через phone, ни через username; требуется OTP.

Миграция 011 однократно отзывает токены и коды переноса, созданные до исправления.
История и аккаунты сохраняются. Порядок обновления: [deploy.md](deploy.md).


## Pre-key пакет (X3DH)

`GET /v1/users/{username}/prekeys`

Возвращает публичный ключевой материал пользователя для инициализации X3DH-рукопожатия.
Забирает один одноразовый pre-key (удаляется после выдачи).

**Ответ `200`:**

```json
{
  "id": "<user_id>",
  "username": "alice",
  "identity_ed25519": "<base64>",
  "identity_x25519": "<base64>",
  "signed_prekey": "<base64>",
  "signed_prekey_signature": "<base64>",
  "one_time_prekey": "<base64 или \"\">",
  "key_version": 2,
  "registration_id": 42,
  "signed_prekey_id": 100,
  "one_time_prekey_id": 101,
  "device_id": 1
}
```

Если одноразовые pre-key исчерпаны, `one_time_prekey` — пустая строка; клиент использует
только signed pre-key.
При отсутствии OTP его id равен 0; в libsignal PreKeyBundle передаются -1 и null.
Signed pre-key, metadata и выдаваемый OTP берутся одной атомарной операцией.

**Ошибки:** `404` (пользователь не найден).

## Сообщения

### Отправить сообщение

`POST /v1/messages` — **требует токен**

Отправляет **уже зашифрованное на клиенте** сообщение получателю. Сервер не расшифровывает.

**Запрос:**

```json
{
  "recipient_id": "<user_id получателя>",
  "ciphertext": "<base64 — зашифрованный блоб>",
  "client_message_id": "unique-id-persisted-before-send",
  "expires_in": 0
}
```

**Ответ `201`:**

```json
{
  "id": "<message_id>",
  "sender_id": "<user_id>",
  "recipient_id": "<user_id>",
  "ciphertext": "<base64>",
  "created_at": "2026-09-06T14:00:00Z"
}
```

Одновременно сообщение уходит получателю через WebSocket (если онлайн).

`client_message_id` необязателен для старых клиентов. Новый клиент сохраняет
его до отправки и повторяет тот же ciphertext, адресацию и expires_in. В пределах
30 дней повтор возвращает прежние id/created_at/expires_at без второй записи.
Изменение содержимого при том же id даёт 409. Ответ отправки содержит
`client_message_id`. Квитанция сохраняется после истечения сообщения, чтобы
повтор не воскресил удалённую запись. Старше 30 дней повтор безопасным не считается.

Пустой ciphertext, отрицательный expires_in и TTL более 2592000 секунд дают 400.
Идентификатор повтора — до 128 символов a-z A-Z 0-9 _ -. Квитанция содержит
хэш запроса, id и время результата, без тела сообщения.

**Ошибки:** `401` (без/неверный токен), `404` (получатель не найден), `400` (невалидный body).

### Получить сообщения

`GET /v1/messages?since=<RFC3339>&after_id=<id>&limit=200` — **требует токен**

Возвращает входящие DM и сообщения групп, где пользователь состоит.
Исходящие DM не входят в inbox: клиент хранит их локальную копию.
По умолчанию since=Unix epoch, limit=200; допустимый limit от 1 до 500.
Без after_id условие строго created_at > since. С after_id дополнительно включаются
записи с created_at=since и id > after_id. Сортировка — created_at, id.
Следующую страницу запрашивают по времени и id последнего сообщения предыдущей.
Точность дат — RFC3339 с дробной частью; сохраняйте её полностью.
Повреждённая дата или limit дают 400. Для защиты от поздних коммитов клиенту нужны
перекрытие курсоров и периодическая полная сверка; выдача не является снимком БД.

**Ответ `200`:**

```json
{
  "messages": [
    {
      "id": "<message_id>",
      "sender_id": "<user_id>",
      "recipient_id": "<user_id>",
      "ciphertext": "<base64>",
      "created_at": "2026-09-06T14:00:00Z"
    }
  ]
}
```

## Медиа

Медиа передаётся **только как ciphertext**. Ключ, nonce, исходное имя файла и настоящий
MIME клиент передаёт получателю внутри E2E-сообщения (через `/v1/messages`), а не в
открытых полях загрузки.

### Загрузить медиа

`POST /v1/media` — **требует токен**

`multipart/form-data`:
- `file` — обязательное поле, сами зашифрованные байты (не base64).
- `content_type` — необязательно, MIME (по умолчанию `application/octet-stream`).

Лимит — `MAX_MEDIA_BYTES` (по умолчанию 50 MiB), относится к ciphertext.

**Ответ `201`:**

```json
{ "id": "<media_id>", "content_type": "application/octet-stream", "size": 528 }
```

### Скачать медиа

`GET /v1/media/{id}` — **требует токен**

Отдаёт сырые байты ciphertext. Заголовки: `Content-Type` из метаданных, `Content-Length`,
`Content-Disposition: attachment`, `X-Content-Type-Options: nosniff`,
`Cache-Control: private, no-store`.

**Ошибки медиа:** `400` (нет file/повреждённый multipart), `404` (нет метаданных/файла),
`409` (конфликт id), `413` (превышен лимит), `500` (ошибка хранилища), `503` (BlobStore не подключён).

## Группы, каналы, контакты

Все эндпоинты требуют Bearer-токен. Групповые сообщения — тоже ciphertext: сервер
хранит и рассылает их, не расшифровывая. Групповые ключи (Sender Keys / MLS) живут
на клиентах и через API не передаются.

### Создать группу / канал

`POST /v1/groups`, `POST /v1/channels` — body `{"title": "..."}` (1–200 символов).

**Ответ `201`:** `{"id":"...","type":"group|channel","title":"...","created_by":"...","created_at":"..."}`
Создатель автоматически становится `owner`.

### Список чатов

`GET /v1/chats` → `{"chats":[ ...chat... ]}` (чаты, где пользователь участник).

### Участники

- `POST /v1/chats/{id}/members` — body `{"user_id":"..."}`. В группу добавляет
  owner/admin; в канал любой может подписаться сам (`user_id` = свой id), добавлять
  других — только owner/admin. Ответ `201`.
- `DELETE /v1/chats/{id}/members/{user_id}` — удалить участника (owner/admin);
  удаление owner → `403`.
- `GET /v1/chats/{id}/members` → `{"members":[{"user_id","role","joined_at"}]}`.

Неучастник получает `404` (существование чата не раскрывается).

### Сообщения в чате

`POST /v1/chats/{id}/messages` — body `{"ciphertext":"<base64>"}`. Писать в группу
может любой участник, в канал — только owner/admin. Сообщение сохраняется один раз
и рассылается всем участникам через WebSocket.
Поля expires_in и client_message_id имеют те же правила, что у личных сообщений.
Групповое E2E на Android ещё не реализовано; этот маршрут описывает серверный транспорт.

**Ответ `201`:** `{"id","sender_id","chat_id","ciphertext","created_at"}`.

Получение — через общий `GET /v1/messages` (возвращает и личные, и групповые).

### Контакты

- `POST /v1/contacts` — body `{"contact_id":"..."}` → `201`.
- `GET /v1/contacts` → `{"contacts":["<user_id>", ...]}`.

### Поиск контактов по телефонной книге

`POST /v1/contacts/discover` — **требует токен**

Находит, кто из телефонной книги уже зарегистрирован в Umbra. Клиент НЕ отправляет
номера в открытом виде: он нормализует их (те же правила, что при регистрации)
и присылает только хэши `SHA-256("umbra-phone:" || номер E.164)` в hex.

**Запрос:**

```json
{ "hashes": ["<64 hex-символа>", "..."] }
```

До 1000 хэшей за запрос; дубликаты игнорируются. Отдельный лимит — 30 запросов/мин
на IP (сдерживание перебора номеров: пространство телефонных номеров невелико,
поэтому хэши в принципе перебираемы — свойство всех схем без SGX/PSI).

**Ответ `200`:**

```json
{
  "matches": [
    {
      "id": "<user_id>",
      "username": "u79994445566",
      "display_name": "Борис",
      "phone": "+79994445566",
      "phone_hash": "<hex>"
    }
  ]
}
```

`phone_hash` в ответе позволяет клиенту сопоставить совпадение с записью телефонной
книги. Пользователи без номера (legacy-аккаунты) в поиске не участвуют.

**Ошибки:** `400` (невалидный хэш, >1000 хэшей), `401` (нет токена), `429` (лимит).

### «Печатает»

- `POST /v1/chats/{id}/typing` — отметить (эфемерно, TTL 5 с).
- `GET /v1/chats/{id}/typing` → `{"typing":["<user_id>", ...]}`.

Индикатор хранится в памяти и не логируется — метаданные «кто когда печатал» не сохраняются.

## Звонки (WebRTC-сигналинг)

Сервер хранит только метаданные звонка и ретранслирует сигналы; **медиа-поток идёт
peer-to-peer (WebRTC)** и через сервер не проходит. Сигналы НЕ сохраняются (только
ретрансляция через WebSocket).

### Начать звонок

`POST /v1/calls` — body `{"callee_id":"...","video":false}`.

**Ответ `201`:** запись звонка со статусом `ringing`. Вызываемый получает WebSocket-событие
`{"type":"call","data":{...звонок...}}`.

### Ретрансляция сигнала

`POST /v1/calls/{id}/signal` — body `{"to":"<второй участник>","kind":"offer|answer|ice","payload":{...}}`.
`payload` — произвольный JSON (SDP/ICE-кандидат). Сервер пересылает его второму участнику
через WebSocket-событие `{"type":"call_signal","data":{"call_id","from","kind","payload"}}`.

### Смена статуса

`POST /v1/calls/{id}/status` — body `{"status":"active|ended|declined|missed"}`.
Второй участник получает `{"type":"call_status","data":{"call_id","status"}}`.
При `ended`/`declined`/`missed` выставляется `ended_at`.

### История звонков

`GET /v1/calls` → `{"calls":[{"id","caller_id","callee_id","video","status","created_at","ended_at"}]}`.

Проверки прав: участвовать в сигналинге/смене статуса может только участник звонка
(иначе `403`); посторонний не знает о существовании звонка.

## Секретные сообщения и аккаунт

### Самоуничтожение сообщений

В `POST /v1/messages` и `POST /v1/chats/{id}/messages` добавлено необязательное поле
`expires_in` (0–2592000 секунд). При значении > 0 срок начинается с первого
приёма сервером. Повтор не продлевает срок. Просроченное не выдаётся через REST
и удаляется фоновой задачей примерно каждые 10 секунд. Android также удаляет
истёкшие локальные записи во время работы процесса и после запуска.
Самоуничтожение не удаляет чужие копии, бэкапы или уже отправленные WS-кадры.

### «Сжечь» аккаунт

`POST /v1/account/burn` — полностью и необратимо удаляет аккаунт текущего пользователя:
ключи, токены, сообщения (отправленные и адресованные), метаданные медиа,
созданные им чаты, членство в чужих чатах, контакты и звонки.
Сообщения других авторов в чужих группах сохраняются. При удалении созданного
пользователем чата удаляется вся его серверная история.
Файлы ставятся в постоянную очередь удаления; сбои хранилища повторяются фоном.
Ответ: `200 {"status":"burned","deleted_at":"...","cleanup_pending":false}`.
cleanup_pending=true означает, что очередь файлов ещё не завершена.
После этого токен невалиден, username освобождается.

`GET /v1/account` — возвращает `{id, username, phone, display_name, created_at, key_version, one_time_prekey_count}`
(`phone`/`display_name` пустые у legacy-аккаунтов, зарегистрированных только по username).
После «сжечь» аккаунт освобождается и номер телефона: на нём можно зарегистрироваться заново.

## Realtime (WebSocket)

`GET /v1/ws` с `Authorization: Bearer <token>`.
Query-параметр token сохранён только для совместимости; новый Android его не использует.

Устанавливает WebSocket-соединение для server-push. Клиент ничего содержательного по WS
не отправляет (приём сообщений — по REST); WS нужен для мгновенной доставки.

**События (JSON-фреймы):**

```json
{ "type": "message", "data": { "id": "...", "sender_id": "...", "recipient_id": "...", "ciphertext": "...", "created_at": "..." } }
```

Сервер держит соединение alive (ping каждые 50 с, pong-таймаут 60 с).
Токен перепроверяется перед отправкой и раз в 10 секунд. При переполнении очереди
соединение закрывается, клиент восстанавливает сообщения через REST. Origin должен
отсутствовать (нативный клиент) либо совпадать с https://Host.

## Коды ошибок

| Код | Значение |
|---|---|
| `400` | Невалидный запрос/body |
| `401` | Нет/неверный/истёкший токен, неверная подпись |
| `404` | Объект не найден |
| `409` | Конфликт (username занят, номер уже зарегистрирован, конфликт id медиа) |
| `413` | Превышен лимит размера |
| `429` | Превышен лимит запросов или число challenge |
| `500` | Внутренняя ошибка |
| `503` | Хранилище недоступно |

---

Лимиты запросов и условия запуска описаны в deploy.md. Формат ciphertext Android v2:
base64 от байтов U M B 0x02, типа libsignal и сериализованного сообщения libsignal.
Это контейнер транспорта; криптография выполняется библиотекой Signal.
