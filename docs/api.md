# API Umbra — контракт эндпоинтов

Сверено с исходниками сервера 9 сентября 2026. Источник истины —
`internal/httpapi/server.go` (регистрация маршрутов) и `internal/httpapi/ratelimit.go`
(лимиты). Текущий клиент — Android 0.6.0, versionCode 10: добавлены звонки на
WebRTC поверх существующих маршрутов сигналинга, сервер не менялся.

Все запросы и ответы — JSON, кроме тела медиа-блобов и WebSocket-кадров. Бинарные
данные внутри JSON — base64. Аутентификация — Bearer-токен.

Базовый URL: `https://<ваш-домен>` (продакшн) или `http://localhost:8080` (локально).

---

## Модель хранения: T1, без сквозного шифрования

Это нужно понимать до чтения остального контракта.

- Сообщения хранит сервер, и для владельца сервера они доступны. Сквозного
  шифрования в текущей версии **нет**.
- Поле `ciphertext` — **историческое имя**. Android кладёт в него
  `base64(utf8(JSON))`, где JSON — конверт `MessageContent`:

  ```json
  { "v": 1, "kind": "text", "text": "привет", "media": null }
  ```

  При `kind: "media"` в `media` лежит `{ "id", "mime", "size", "name" }`.
  При `kind: "voice"` (голосовое сообщение, клиент 0.5.0 и новее) —
  `{ "id", "mime": "audio/mp4", "size", "durationMs" }`: `id` — запись, загруженная
  через `POST /v1/media`, `durationMs` — длительность в миллисекундах.

  ```json
  { "v": 1, "kind": "voice", "text": "", "media": { "id": "<media_id>", "mime": "audio/mp4", "size": 41231, "durationMs": 7400 } }
  ```

  Поле `durationMs` опускается, если равно 0. Клиенты 0.4.2 и старше этот `kind`
  не знают и показывают заглушку вместо записи.
  Определение — `android/app/src/main/java/com/umbra/app/data/msg/MessageContent.kt`.
- Сервер конверт не разбирает: делает base64-decode при приёме и base64-encode при
  выдаче, поэтому возвращаемый base64 идентичен отправленному. Для сервера это
  непрозрачный блоб, но не зашифрованный.
- Приватность модели — «доверяй серверу»: TLS на транспорте плюс доверие владельцу
  сервера. Используйте HTTPS.
- Разделы про X3DH, pre-key пакеты и `key_version=2` относятся **только** к
  legacy-клиентам прежней Signal-модели. Текущий Android их не использует.

## Общие положения

### Формат ошибок

Все ошибки возвращаются в виде:

```json
{ "error": "описание" }
```

Часть сообщений об ошибках возвращается на русском языке (проверка кода, имени
профиля) — они предназначены для показа пользователю.

### Аутентифицированные запросы

Заголовок:

```
Authorization: Bearer <token>
```

Токен выдаётся после `verify_code`, срок — `TOKEN_TTL_SECONDS` (по умолчанию
2592000 секунд, 30 дней после входа или последнего продления). Сервер хранит
только SHA-256 хэш токена.

## Лимиты запросов

Окно — одна минута на сетевой адрес, отдельный счётчик на категорию. При
превышении сервер отвечает `429` с заголовком `Retry-After: 60`.

| Категория | Маршруты | Лимит в минуту |
|---|---|---|
| `otp_request` | `POST /v1/auth/request_code` | **6** |
| `transfer` | `POST /v1/account/transfer/claim` | 20 |
| `register` | `POST /v1/register` | 30 |
| `discover` | `POST /v1/contacts/discover` | 30 |
| `otp_verify` | `POST /v1/auth/verify_code` | 30 |
| `auth` | остальные `/v1/auth/*` и `*/prekeys` | 120 |
| `api` | все прочие маршруты | 600 |

`GET /healthz` проходит без учёта лимитов. Общее число активных счётчиков
ограничено 16384; при переполнении новые адреса получают `429` до истечения окна.

`X-Forwarded-For` учитывается **только** если непосредственный peer входит в
`TRUSTED_PROXIES`. Иначе используется адрес соединения. Подробности и настройка
за Caddy — [deploy.md](deploy.md).

## Аутентификация по номеру

Текущий Android использует номер телефона и одноразовый шестизначный код.

### Запрос кода

`POST /v1/auth/request_code` — без токена.

```json
{ "phone": "+79994445566" }
```

Код приходит **владельцу Umbra** в Telegram-чат `TELEGRAM_CHAT_ID`; владелец
передаёт код пользователю. Это не SMS и не сообщение в личный Telegram
регистрирующегося, поэтому владением SIM-картой это не подтверждается.

Код действует 5 минут, хранится в памяти процесса (при перезапуске сервера
невыданные коды теряются). Аккаунт для запроса не нужен: один и тот же маршрут
обслуживает и вход, и регистрацию.

**Ответ `200`:**

```json
{ "status": "sent", "expires_in": "5 минут" }
```

**Ошибки:** `400` (невалидное тело или номер), `429` (лимит 6/мин),
`502` (Telegram не принял отправку), `503` (`TELEGRAM_BOT_TOKEN` или
`TELEGRAM_CHAT_ID` не настроены), `500`.

### Проверка кода

`POST /v1/auth/verify_code` — без токена.

```json
{ "phone": "+79994445566", "code": "123456" }
```

Из кода отбрасываются все нецифровые символы; после нормализации должно остаться
ровно 6 цифр. Код одноразовый, допускается до 5 неверных попыток.

Если аккаунт с номером есть — вход. Если нет — создаётся облачный аккаунт:
`username` = `u` + цифры номера без `+`, Signal-ключи фиктивные (в модели T1 не
используются), `key_version` = 1. Один аккаунт на номер.

**Ответ `200`:**

```json
{
  "token": "<opaque>",
  "expires_at": "2026-10-09T12:00:00Z",
  "new_account": true,
  "profile_complete": false,
  "account": {
    "id": "<user_id>",
    "username": "u79994445566",
    "phone": "+79994445566",
    "display_name": "",
    "last_name": "Иванов",
    "avatar_media_id": "<media_id>"
  }
}
```

`last_name` и `avatar_media_id` опускаются, если пусты. `profile_complete` = false,
пока не заполнено `display_name`; клиент в этом случае ведёт на экран профиля.

**Ошибки:** `400` (невалидное тело, номер или длина кода), `401` («неверный код»),
`404` («код не найден или истёк»), `429` (лимит 30/мин либо более 5 попыток),
`503`, `500`.

Обратите внимание: неверный код — это `401`, а истёкший или отсутствующий — `404`.

## Сессия

### Продление

`POST /v1/auth/refresh` — **требует токен**, без тела.

**Ответ `200`:** `{"expires_at":"2026-10-09T12:00:00Z"}` (RFC3339 с наносекундами),
заголовок `Cache-Control: no-store`.

Продлевает только действующий токен того же пользователя. Сам токен остаётся
прежним, поэтому запрос можно безопасно повторить после потери ответа. Проверка
отзыва и продление выполняются одной атомарной операцией.

Android вызывает маршрут при полной синхронизации: при запуске, переподключении и
примерно раз в 15 минут. Старый сервер, отвечающий `404`/`405`, продолжает
обслуживать клиент, но без продления — нужно обновить сервер.

**Ошибки:** `401` (истёкший или отозванный токен), `503` (сбой хранилища).

### Выход

`POST /v1/auth/logout` — **требует токен**. Отзывает предъявленный токен и
разрывает WebSocket-соединения аккаунта; другие сессии могут переподключиться.

**Ответ `200`:** `{"status":"logged_out"}`.

## Legacy-вход по ключу

`POST /v1/register`, `POST /v1/auth/challenge`, `POST /v1/auth/verify` по умолчанию
возвращают `410`. `ALLOW_LEGACY_AUTH=true` включает их **только** для аккаунтов
без номера телефона. В регистрации обязательны username и корректный набор
ключей; переданный `phone` отклоняется с `403`. Уже существующий телефонный
аккаунт нельзя авторизовать по ключу ни через `phone`, ни через `username` —
требуется OTP.

Миграция 011 однократно отзывает токены и коды переноса, созданные до этого
исправления. История и аккаунты сохраняются. Порядок обновления —
[deploy.md](deploy.md).

### Обновление ключевого материала

`PUT /v1/account/keys` — **требует токен**. Публикует ключи `key_version=2` для
legacy-клиентов. Маршрут доступен любому авторизованному пользователю и **не**
закрывается флагом `ALLOW_LEGACY_AUTH`; текущий Android его не вызывает.

Тело — тот же набор полей, что в `POST /v1/register`: `identity_x25519`,
`signed_prekey`, `signed_prekey_signature`, `key_version`, `registration_id`,
`signed_prekey_id`, `one_time_prekeys[]`, `one_time_prekey_ids[]`.
Лимит тела — 1 MiB.

**Ответ `200`:** `{"status":"updated"}`.

**Ошибки:** `400` (невалидное тело, `key_version` не 2, повреждённый ключевой
материал), `404` (пользователь не найден), `409` («identity change is not
allowed» — сменить identity-ключ нельзя), `500`.

## Профиль и аватар

### Обновить профиль

`POST /v1/account/profile` — **требует токен**. Используется и для завершения
регистрации, и для последующего редактирования. Лимит тела — 64 KiB.

```json
{ "username": "boris", "name": "Борис", "last_name": "Иванов" }
```

- `name` — **обязательно всегда**, даже если меняется только `username`. Пустое
  имя отклоняется с `400` и сообщением «Введите имя».
- `username` — необязательно. Пустая строка сохраняет текущий никнейм.
  Правила: 3–32 символа, ASCII-буквы, цифры и `_`.
- `last_name` — трёхзначное поле: отсутствует или `null` сохраняет фамилию,
  явная пустая строка `""` удаляет её. Максимум 64 символа.

**Ответ `200`:**

```json
{ "id": "<user_id>", "username": "boris", "display_name": "Борис", "last_name": "Иванов" }
```

**Ошибки:** `400` (невалидное тело, пустое или некорректное имя, некорректный
username, `last_name` длиннее 64 символов), `404` (пользователь не найден),
`409` («username already taken»), `503`, `500`.

### Установить аватар

`POST /v1/account/avatar` — **требует токен**. Лимит тела — 64 KiB.

```json
{ "media_id": "<media_id>" }
```

Медиа предварительно загружается через `POST /v1/media`. Сервер проверяет, что
блоб принадлежит текущему аккаунту.

**Ответ `200`:** `{"status":"ok","avatar_media_id":"<media_id>"}`.

**Ошибки:** `400` (пустой `media_id`), `403` («media belongs to another account»),
`404` (медиа не найдено), `503`, `500`.

### Получить свой аккаунт

`GET /v1/account` — **требует токен**.

**Ответ `200`:**

```json
{
  "id": "<user_id>",
  "username": "boris",
  "phone": "+79994445566",
  "display_name": "Борис",
  "last_name": "Иванов",
  "created_at": "2026-09-06T14:00:00Z",
  "key_version": 1,
  "one_time_prekey_count": 0,
  "avatar_media_id": "<media_id>"
}
```

`phone` и `display_name` пустые у legacy-аккаунтов, зарегистрированных только по
username. После «сжечь» освобождается и номер: на нём можно зарегистрироваться
заново.

**Ошибки:** `404` (пользователь не найден), `503`, `500`.

## Карточки пользователей

Публичная карточка для диалогов и списков участников. Телефон в неё **не входит**.

```json
{
  "id": "<user_id>",
  "username": "boris",
  "display_name": "Борис",
  "last_name": "Иванов",
  "avatar_media_id": "<media_id>",
  "created_at": "2026-09-06T14:00:00Z"
}
```

`last_name` и `avatar_media_id` опускаются, если пусты.

### По идентификатору

`GET /v1/users/{user_id}` — **требует токен**. Требует авторизации, но не общего
чата или контакта: в семейной сети это допустимо.

**Ошибки:** `400` (пустой `user_id`), `404`, `503`.

### По никнейму

`GET /v1/by-username/{username}` — **требует токен**. Ведущий `@` отбрасывается.
Нужен для сценария «новый диалог по никнейму».

**Ошибки:** `400` (никнейм не проходит проверку формата), `404`, `503`.

## Pre-key пакет (legacy X3DH)

> Раздел относится только к прежней Signal-модели. Текущий Android эти данные не
> запрашивает и не использует.

`GET /v1/users/{username}/prekeys` — без токена.

Возвращает публичный ключевой материал для инициализации X3DH-рукопожатия.
Забирает один одноразовый pre-key (удаляется после выдачи).

**Ответ `200`:**

```json
{
  "id": "<user_id>",
  "username": "alice",
  "identity_ed25519": "<base64>",
  "identity_x25519": "<base64>",
  "signed_prekey": "<base64>",
  "signed_prekey_signature": "<base64>",
  "one_time_prekey": "<base64 или \"\">",
  "key_version": 2,
  "registration_id": 42,
  "signed_prekey_id": 100,
  "one_time_prekey_id": 101,
  "device_id": 1
}
```

Если одноразовые pre-key исчерпаны, `one_time_prekey` — пустая строка, а его id
равен 0; клиент использует только signed pre-key (в libsignal PreKeyBundle
передаются -1 и null). Signed pre-key, metadata и выдаваемый OTP берутся одной
атомарной операцией.

**Ошибки:** `404` (пользователь не найден).

## Сообщения

### Отправить сообщение

`POST /v1/messages` — **требует токен**. Лимит тела — `MAX_MESSAGE_BYTES`
(по умолчанию 2 MiB).

Сервер сохраняет содержимое `ciphertext` как непрозрачный блоб и не разбирает
его. Это **не** означает шифрование — см. [модель T1](#модель-хранения-t1-без-сквозного-шифрования).

**Запрос:**

```json
{
  "recipient_id": "<user_id получателя>",
  "ciphertext": "<base64 конверта JSON>",
  "client_message_id": "unique-id-persisted-before-send",
  "expires_in": 0
}
```

**Ответ `201`:**

```json
{
  "id": "<message_id>",
  "sender_id": "<user_id>",
  "recipient_id": "<user_id>",
  "ciphertext": "<base64>",
  "created_at": "2026-09-06T14:00:00Z"
}
```

Одновременно сообщение уходит получателю через WebSocket, если он онлайн.

`client_message_id` необязателен для старых клиентов. Новый клиент сохраняет его
до отправки и повторяет тот же `ciphertext`, адресацию и `expires_in`. В пределах
30 дней повтор возвращает прежние `id`/`created_at`/`expires_at` без второй
записи. Изменение содержимого при том же id даёт `409`. Ответ отправки содержит
`client_message_id`. Квитанция сохраняется после истечения сообщения, чтобы
повтор не воскресил удалённую запись. Повтор старше 30 дней безопасным не считается.

Пустой `ciphertext`, отрицательный `expires_in` и TTL более 2592000 секунд дают
`400`. Идентификатор повтора — до 128 символов из `a-z A-Z 0-9 _ -`. Квитанция
содержит хэш запроса, id и время результата, без тела сообщения.

**Ошибки:** `400` (невалидное тело), `401`, `404` (получатель не найден),
`409` (тот же `client_message_id` с другим содержимым), `413` (превышен лимит тела).

### Получить сообщения

`GET /v1/messages?since=<RFC3339>&after_id=<id>&limit=200` — **требует токен**

Возвращает входящие личные сообщения и сообщения групп, где пользователь состоит.
Исходящие личные сообщения в inbox не входят: клиент хранит их локальную копию.

По умолчанию `since` = Unix epoch, `limit` = 200; допустимый `limit` — от 1 до 500.
Без `after_id` условие строго `created_at > since`. С `after_id` дополнительно
включаются записи с `created_at = since` и `id > after_id`. Сортировка —
`created_at`, затем `id`. Следующую страницу запрашивают по времени и id
последнего сообщения предыдущей.

Точность дат — RFC3339 с дробной частью секунды; **сохраняйте её полностью**,
иначе пагинация зациклится. Повреждённая дата или `limit` дают `400`. Выдача не
является снимком БД: для защиты от поздних коммитов клиенту нужны перекрытие
курсоров и периодическая полная сверка.

**Ответ `200`:**

```json
{
  "messages": [
    {
      "id": "<message_id>",
      "sender_id": "<user_id>",
      "recipient_id": "<user_id>",
      "ciphertext": "<base64>",
      "created_at": "2026-09-06T14:00:00Z"
    }
  ]
}
```

## Медиа

Сервер хранит загруженные байты как есть и не анализирует их. Имя файла и MIME,
которые видит получатель, передаются в конверте сообщения (поле `media`), а не в
полях загрузки.

В текущем Android медиа используется для **аватаров и голосовых сообщений**.
Голосовое сообщение — обычная загрузка `audio/mp4` через `POST /v1/media`, а затем
сообщение с конвертом `kind: "voice"`. Отправка остальных вложений (файлы, фото,
видео) не реализована, хотя серверные маршруты работают.

Серверных изменений для голосовых сообщений не требуется: `content_type` не ограничен
списком, проверяется только формат `type/subtype`. Загруженный блоб без сообщения
считается «сиротой» и удаляется сборщиком мусора через 24 часа, поэтому порядок
«сначала загрузка, потом сообщение» безопасен.

### Загрузить медиа

`POST /v1/media` — **требует токен**

`multipart/form-data`:
- `file` — обязательное поле, сами байты (не base64).
- `content_type` — необязательно, MIME (по умолчанию `application/octet-stream`).

Лимит — `MAX_MEDIA_BYTES` (по умолчанию 50 MiB), относится к содержимому файла
без multipart-обвязки. Дополнительно действует квота `MAX_USER_MEDIA_BYTES` на
суммарный объём пользователя (0 = без квоты). Параллельных загрузок — не более
восьми на экземпляр сервера.

**Ответ `201`:**

```json
{ "id": "<media_id>", "content_type": "application/octet-stream", "size": 528 }
```

### Скачать медиа

`GET /v1/media/{id}` — **требует токен**

Отдаёт сырые байты. Заголовки: `Content-Type` из метаданных, `Content-Length`,
`Content-Disposition: attachment`, `X-Content-Type-Options: nosniff`,
`Cache-Control: private, no-store`.

**Ошибки медиа:** `400` (нет `file` или повреждённый multipart), `404` (нет
метаданных или файла), `409` (конфликт id), `413` (превышен лимит или квота),
`500` (ошибка хранилища), `503` (BlobStore не подключён).

## Группы, каналы, контакты

Все эндпоинты требуют Bearer-токен. Групповые сообщения хранятся и рассылаются
сервером в том же виде, что личные: конверт в поле `ciphertext`, без сквозного
шифрования. Группового E2E в текущей версии нет.

### Создать группу или канал

`POST /v1/groups`, `POST /v1/channels` — body `{"title": "..."}` (1–200 символов).

**Ответ `201`:**
`{"id":"...","type":"group|channel","title":"...","created_by":"...","created_at":"..."}`
Создатель автоматически становится `owner`.

### Список чатов

`GET /v1/chats` → `{"chats":[ ...chat... ]}` — чаты, где пользователь участник,
включая пустые.

### Участники

- `POST /v1/chats/{id}/members` — body `{"user_id":"..."}`. В группу добавляет
  owner или admin; в канал любой может подписаться сам (`user_id` = свой id),
  добавлять других — только owner/admin. Ответ `201`.
- `DELETE /v1/chats/{id}/members/{user_id}` — удалить участника (owner/admin);
  удаление owner → `403` («cannot remove owner»).
- `GET /v1/chats/{id}/members` → `{"members":[{"user_id","role","joined_at"}]}`.

Неучастник получает `404`: существование чата не раскрывается. Недостаток прав
внутри чата — `403`.

### Сообщения в чате

`POST /v1/chats/{id}/messages` — body `{"ciphertext":"<base64>"}`. Писать в группу
может любой участник, в канал — только owner/admin. Сообщение сохраняется один
раз и рассылается всем участникам через WebSocket.

Поля `expires_in` и `client_message_id` работают по тем же правилам, что у личных
сообщений.

**Ответ `201`:** `{"id","sender_id","chat_id","ciphertext","created_at"}`.

Получение — через общий `GET /v1/messages`, он возвращает и личные, и групповые.

### Контакты

- `POST /v1/contacts` — body `{"contact_id":"..."}` → `201`.
- `GET /v1/contacts` → `{"contacts":["<user_id>", ...]}`.

### Поиск контактов по телефонной книге

`POST /v1/contacts/discover` — **требует токен**

Находит, кто из телефонной книги уже зарегистрирован в Umbra. Клиент не отправляет
номера в открытом виде: он нормализует их теми же правилами, что при регистрации,
и присылает только хэши `SHA-256("umbra-phone:" || номер E.164)` в hex.

**Запрос:**

```json
{ "hashes": ["<64 hex-символа>", "..."] }
```

До 1000 хэшей за запрос, дубликаты игнорируются. Лимит — 30 запросов в минуту.
Это сдерживание перебора: пространство телефонных номеров невелико, поэтому хэши
в принципе перебираемы — свойство всех схем без SGX/PSI.

**Ответ `200`:**

```json
{
  "matches": [
    {
      "id": "<user_id>",
      "username": "u79994445566",
      "display_name": "Борис",
      "phone": "+79994445566",
      "phone_hash": "<hex>"
    }
  ]
}
```

`phone_hash` в ответе позволяет клиенту сопоставить совпадение с записью
телефонной книги. Пользователи без номера (legacy-аккаунты) в поиске не участвуют.

**Ошибки:** `400` (невалидный хэш, больше 1000 хэшей), `401`, `429`.

### «Печатает»

- `POST /v1/chats/{id}/typing` — отметить, эфемерно, TTL 5 секунд.
- `GET /v1/chats/{id}/typing` → `{"typing":["<user_id>", ...]}`.

Индикатор хранится в памяти процесса и не логируется: метаданные «кто когда
печатал» не сохраняются.

## Звонки (сигналинг)

> **Состояние реализации.** Android 0.6.0 использует все четыре маршрута:
> `POST /v1/calls` создаёт вызов, `POST /v1/calls/{id}/signal` переносит offer,
> answer и ICE-кандидатов, `POST /v1/calls/{id}/status` меняет статус,
> `GET /v1/calls` отдаёт журнал. Инициатор всегда отправляет offer, вызываемый —
> answer; ICE-кандидаты идут в обе стороны и делят общий лимит категории `api`
> (600 запросов в минуту). Медиа-поток через сервер **не проходит**: звук и видео
> идут напрямую между устройствами, при необходимости — через TURN: адреса и
> временную учётку клиент забирает через `GET /v1/turn` (см.
> [deploy.md](deploy.md)). Клиенты 0.5.0 и старше маршрут сигналинга не вызывают
> и остаются без звука.

### Начать звонок

`POST /v1/calls` — body `{"callee_id":"...","video":false}`.

**Ответ `201`:** запись звонка со статусом `ringing`. Вызываемый получает
WebSocket-событие `{"type":"call","data":{...звонок...}}`.

### Ретрансляция сигнала

`POST /v1/calls/{id}/signal` — body
`{"to":"<второй участник>","kind":"offer|answer|ice","payload":{...}}`.
`payload` — произвольный JSON (SDP или ICE-кандидат). Сервер пересылает его
второму участнику через WebSocket-событие
`{"type":"call_signal","data":{"call_id","from","kind","payload"}}`.
Сигналы не сохраняются.

### Смена статуса

`POST /v1/calls/{id}/status` — body `{"status":"active|ended|declined|missed"}`.

**Ответ `200`:** `{"status":"ended"}` — только поле `status`, а не полный объект
звонка. Второй участник получает
`{"type":"call_status","data":{"call_id","status"}}`. При `ended`, `declined` или
`missed` выставляется `ended_at`.

### История звонков

`GET /v1/calls` →
`{"calls":[{"id","caller_id","callee_id","video","status","created_at","ended_at"}]}`.

### ICE-серверы

`GET /v1/turn` →
`{"ice_servers":[{"urls":["stun:…"]},{"urls":["turn:…"],"username":"…","credential":"…"}],"ttl":3600}`.

Учётка TURN временная: сервер подписывает её общим секретом coturn
(`TURN_SECRET`, схема `use-auth-secret`), и постоянный пароль в приложение не
попадает. `ttl` — срок жизни в секундах (`TURN_TTL_SECONDS`, по умолчанию
3600). Если секрет не задан, отдаётся постоянная пара
`TURN_USERNAME`/`TURN_PASSWORD`; без `TURN_URL` в списке остаётся только STUN.
Клиент запрашивает список перед каждым звонком, кэширует его до истечения
срока, а если маршрут недоступен — берёт адреса, зашитые при сборке.

Участвовать в сигналинге и менять статус может только участник звонка, иначе
`403` («not a participant»). Посторонний не узнаёт о существовании звонка.

## Push-уведомления

`POST /v1/push/devices` с телом `{"token":"<токен FCM>","platform":"android"}` →
`{"status":"registered","push_enabled":true}`. Вызов идемпотентен: повторная
регистрация того же токена перезаписывает запись и переносит устройство на
текущий аккаунт. `push_enabled:false` означает, что сервер собран без ключа
Firebase — токен сохранён, но отправлять некому.

`DELETE /v1/push/devices` с тем же телом → `{"status":"deleted"}`. Клиент
вызывает его при выходе из аккаунта, чтобы уведомления не приходили следующему
владельцу устройства. Удалить можно только свой токен: чужой даёт `404`
(«token not found»).

Ограничения тела: не больше 4 КиБ, `token` — до 512 байт, `platform` — только
`android` (пустое значение считается `android`, иное даёт `400`). Оба маршрута
требуют токен авторизации и делят общий лимит категории `api`.

Сервер отправляет **только data-сообщения**, без блока `notification`, поэтому
уведомление рисует приложение, а текст переписки через Google не идёт:

| Событие | Поля `data` | Приоритет и TTL |
|---|---|---|
| новое сообщение | `kind=message`, `sender_id`, `message_id`, `chat_id`, `sender_name` | обычный, 12 часов |
| входящий звонок | `kind=call`, `call_id`, `caller_id`, `video`, `caller_name` | высокий, 45 секунд |
| звонок завершён | `kind=call_ended`, `call_id`, `status` | высокий, 45 секунд |

Push не отправляется, если получатель в этот момент подключён по WebSocket:
событие он уже получил. Если FCM отвечает `UNREGISTERED`, `INVALID_ARGUMENT`,
`404` или `410`, сервер удаляет мёртвый токен сам. Ошибки доставки не влияют на
результат запроса, который их вызвал: сообщение уже сохранено, звонок создан.

## Перенос аккаунта между устройствами

`vault` — непрозрачный блоб, зашифрованный **клиентом**. Сервер хранит только
SHA-256 хэш кода переноса и сам блоб.

### Создать код переноса

`POST /v1/account/transfer` — **требует токен**.

```json
{ "vault": "<base64>", "code": "ABCD-EFGH-JKMN" }
```

`code` необязателен. Он существует для того, чтобы клиент мог зашифровать `vault`
ключом, производным от кода, **до** выгрузки. Если код не передан, сервер
генерирует его сам. Алфавит — `ABCDEFGHJKMNPQRSTVWXYZ23456789` (без похожих
символов), 12 знаков в формате `XXXX-XXXX-XXXX`. Разделители и регистр при вводе
не важны. Прежний неиспользованный код пользователя отзывается.

**Ответ `200`** (не `201`):

```json
{ "code": "ABCD-EFGH-JKMN", "expires_at": "2026-09-09T13:10:00Z" }
```

Код живёт 10 минут. Лимит `vault` — 16 MiB.

**Ошибки:** `400` (невалидное тело, пустой или некорректный `vault`, код не
проходит формат), `413` («vault too large»), `500`.

### Забрать по коду

`POST /v1/account/transfer/claim` — **без токена**. Это единственный маршрут
`/v1/account/*`, не требующий авторизации: код сам является мандатом на получение
блоба. Защита — короткий TTL и жёсткий лимит 20 запросов в минуту.

```json
{ "code": "abcd efgh jkmn" }
```

**Ответ `200`:** `{"vault":"<base64>"}`. Код гасится при первом успешном получении.

**Ошибки:** `400` (невалидное тело или код), `404` («transfer not found or
expired»), `429`, `500`.

## Самоуничтожение сообщений и удаление аккаунта

### Самоуничтожение

В `POST /v1/messages` и `POST /v1/chats/{id}/messages` есть необязательное поле
`expires_in` (0–2592000 секунд). При значении больше 0 срок начинается с первого
приёма сервером; повтор срок не продлевает. Просроченное не выдаётся через REST и
удаляется фоновой задачей примерно каждые 10 секунд. Android также удаляет
истёкшие локальные записи во время работы процесса и после запуска.

Самоуничтожение не удаляет чужие копии, резервные копии и уже отправленные
WebSocket-кадры.

### «Сжечь» аккаунт

`POST /v1/account/burn` — **требует токен**. Полностью и необратимо удаляет
аккаунт: ключи, токены, сообщения (отправленные и адресованные), метаданные
медиа, созданные пользователем чаты, членство в чужих чатах, контакты и звонки.

Сообщения других авторов в чужих группах сохраняются. При удалении созданного
пользователем чата удаляется вся его серверная история. Файлы ставятся в
постоянную очередь удаления; сбои хранилища повторяются фоном. Активные
WebSocket-соединения аккаунта разрываются.

**Ответ `200`:**

```json
{ "status": "burned", "deleted_at": "2026-09-09T13:00:00Z", "cleanup_pending": false }
```

`cleanup_pending: true` означает, что очередь файлов ещё не завершена. После
ответа токен невалиден, username и номер телефона освобождаются.

**Ошибки:** `500`.

## Realtime (WebSocket)

`GET /v1/ws` с `Authorization: Bearer <token>`. Query-параметр `token` сохранён
только для совместимости; новый Android его не использует.

Соединение нужно для server-push. Клиент ничего содержательного по WebSocket не
отправляет: приём сообщений идёт по REST, а WS обеспечивает мгновенную доставку.

**События (JSON-кадры):**

```json
{ "type": "message", "data": { "id": "...", "sender_id": "...", "recipient_id": "...", "ciphertext": "...", "created_at": "..." } }
```

Остальные типы: `call`, `call_signal`, `call_status`.

Сервер держит соединение живым (ping каждые 50 секунд, pong-таймаут 60 секунд).
Токен перепроверяется перед отправкой и раз в 10 секунд. При переполнении очереди
соединение закрывается, и клиент восстанавливает сообщения через REST. Заголовок
`Origin` должен отсутствовать (нативный клиент) либо совпадать с `https://Host`.

## Служебные маршруты

`GET /healthz` — без токена и без учёта лимитов.

**Ответ `200`:** `{"status":"ok"}`.

Используется в Docker Compose и при проверке после развёртывания.

## Коды ошибок

| Код | Значение |
|---|---|
| `400` | Невалидный запрос или тело |
| `401` | Нет, неверный или истёкший токен; неверная подпись; неверный OTP-код |
| `403` | Нет прав: чужое медиа, не участник звонка, недостаточная роль в чате, `phone` в legacy-регистрации |
| `404` | Объект не найден; истёкший OTP-код; неучастник чата |
| `409` | Конфликт: username занят, номер уже зарегистрирован, конфликт id медиа, повтор с другим содержимым, смена identity-ключа |
| `410` | Legacy-вход по ключу отключён (`ALLOW_LEGACY_AUTH=false`) |
| `413` | Превышен лимит размера или квота |
| `429` | Превышен лимит запросов, число challenge или попыток ввода кода |
| `500` | Внутренняя ошибка |
| `502` | Не удалось отправить OTP-код через Telegram |
| `503` | Хранилище недоступно; OTP не настроен; BlobStore не подключён |
