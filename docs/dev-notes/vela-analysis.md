# Анализ референс-проекта «Vela» (аналог Telegram)

> Источник: распакованный архив проекта мессенджера «Vela», собранного в Grok Build.
> Цель документа — зафиксировать, ЧТО мы заимствуем и ЧЕГО сознательно избегаем.
> Никакой код из Vela в Umbra НЕ переносится: стек другой (Go vs TypeScript),
> требования безопасности строже. Переносим только концепции, фиче-лист и UX-референсы.

---

## 1. Что такое Vela

Telegram-подобный веб-мессенджер. Стек: TypeScript, React 19, TanStack Start (SSR),
Vite, Tailwind + Radix UI, деплой Vercel (serverless), БД Neon Postgres (+ PGLite),
авторизация better-auth («Sign in with Grok» через OAuth), WebRTC для звонков.

### Реализованный функционал (это наш готовый фиче-лист)

- [x] Личные чаты (DM), группы, «Избранное» (saved messages), официальный канал
- [x] Текстовые, голосовые, фото-сообщения
- [x] Голосовые и видеозвонки (WebRTC, perfect negotiation)
- [x] Контакты, статус «онлайн» (last seen)
- [x] Индикатор «печатает», reply (ответ на сообщение), unread-счётчики
- [x] Статусы звонков (ringing/active/ended/missed/declined)
- [x] Тумблер E2EE на чат (у нас — всегда включён, см. §3)

## 2. Критический разбор безопасности Vela (что мы НЕ повторяем)

| Аспект | Vela | Проблема | Umbra |
|---|---|---|---|
| E2EE по умолчанию | выключен (тумблер) | сообщения в БД открытым текстом | **всегда включён** |
| Криптосхема | статический ECDH P-256 → AES-GCM | один ключ навсегда | Signal: X3DH + Double Ratchet |
| Forward secrecy | нет | утечка ключа = вся история | да (новый ключ на сообщение) |
| Хранение ключей | `localStorage` (браузер) | легко слить | Android Keystore |
| Идентичность | OAuth email (Grok) | привязка к аккаунту | username + публичные ключи |
| Сервер | Vercel + Neon (чужое облако) | метаданные у провайдера | self-hosted Go + Postgres |
| Realtime | поллинг БД каждые 400 мс | нагрузка, задержка | WebSocket push |

**Вывод:** Vela — хороший UX-прототип, но не приватный мессенджер. Наш Umbra
по всем пунктам сильнее; это и была исходная цель.

## 3. Что мы заимствуем (конкретика)

### 3.1. Фиче-лист → в дорожную карту
Полный набор фич из §1 раскладывается по нашим этапам (см. ASTRA_TASKS.md):
- DM/группы/избранное/канал → Этап 1 (DM) и Этап 3 (группы/каналы)
- медиа (фото/голос) → Этап 2 (у Astra в работе)
- звонки → Этап 4
- контакты, typing, reply, read-статусы, unread → распределить по этапам 1–3
- статусы звонков → Этап 4

### 3.2. Паттерн WebRTC-звонков (Этап 4)
Из `src/lib/calls/voice-call.ts` + `src/lib/multiplayer/signaling.server.ts` берём
**архитектурный паттерн**, а не код:
- **Perfect negotiation** (polite/impolite peer, `makingOffer`/`ignoreOffer` флаги) —
  стандартный способ избежать «сигналинг-гонки» при переподключениях.
- **DB-backed сигналинг**: таблицы `webrtc_peers` (roster, TTL 30 c) и
  `webrtc_signals` (offer/answer/ice, TTL 60 c), поллинг по курсору `since`.
  В Umbra вместо поллинга будет WebSocket-релей сигналов (у нас уже есть хаб).
- **Ключевое отличие:** в Umbra медиа-канал WebRTC ключуется через
  libsignal (SRTP / DTLS fingerprint сверяется вне канала), а сигналинг идёт через
  наш сервер. Ростер и статусы звонков пишутся в наши таблицы.

### 3.3. Схема данных (Этап 3)
Из `migrations/0002_vela.sql` заимствуем модель таблиц как отправную точку:
`chats`, `chat_members`, `messages`, `calls`, `typing`, `contacts`.
Адаптация под Umbra: `messages.body` у нас НЕ хранится открытым текстом —
только `ciphertext BYTEA`; `chat_members` дополняется групповыми ключами (Sender Keys);
`typing`/`calls` — эфемерные, с TTL и без логов «кто когда».

### 3.4. UX-референсы для Android-клиента
Вкладки Chats / Contacts / Calls / Settings, вёрстка пузырей сообщений, reply-превью,
бейдж unread, замок на E2EE-чатах — как референс для Jetpack Compose (Этап 6).
