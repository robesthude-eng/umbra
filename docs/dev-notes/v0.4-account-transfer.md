# v0.4 — вход на новом телефоне с автоподтягиванием данных

Статус: реализация (сервер готов, клиент в работе). Версия «перенос по коду».

## Проблема

Umbra построена как E2EE-мессенджер в модели Signal: пароля нет, аккаунт = пара
ключей на устройстве (Ed25519 для входа, X25519/преключи для шифрования).
Сервер хранит публичные ключи, шифротексты сообщений и медиа-блобов — но не
приватные ключи. Поэтому «просто ввести логин на другом телефоне» в такой модели
невозможно: новый телефон не может ни подписать challenge, ни расшифровать историю.

Сервер, однако, уже умеет отдавать пользователю всю его историю сообщений
(`GET /v1/messages?since=…`), медиа (`GET /v1/media/{id}`), чаты, контакты и звонки.
Значит, если перенести на новый телефон «цифровую личность» (identity + Signal-сессии
+ локальную копию истории), вход и полное восстановление контента возможны
без изменений протокола обмена сообщениями.

## Сценарий (что видит пользователь)

1. На старом телефоне: Настройки → «Перенести на другой телефон».
   Приложение собирает локальный зашифрованный бэкап (личность + вся история),
   шифрует его ключом из одноразового кода и выгружает на сервер. Экран показывает
   код вида `XXXX-XXXX-XXXX` (действует 10 минут).
2. На новом телефоне: установить Umbra → «У меня уже есть аккаунт» → ввести
   код со старого телефона.
3. Приложение скачивает бэкап, расшифровывает, восстанавливает ключи и историю,
   затем выполняет обычный вход (challenge-подпись) и дальше работает как обычно:
   входящие и медиа продолжают приходить/докачиваться с сервера.

Ограничение: одновременная работа двух телефонов не поддерживается (Signal-сессии
рассчитаны на одно устройство). После переноса рекомендуется выйти из приложения
на старом телефоне. Повторный перенос — тем же способом (с активного телефона).

## Серверная часть (реализована)

Хранилище — таблица `account_transfers` (миграция `008_account_transfer.sql`):
непрозрачный `vault` (BYTEA), `code_hash`, `user_id`, `expires_at`, `used`.

API:
- `POST /v1/account/transfer` (auth) — тело `{"vault": "<base64>", "code": "…"}`.
  `code` опционален: клиент может прислать свой код (сервер валидирует формат и
  хэширует), чтобы зашифровать vault ключом из кода ещё до выгрузки. Если код
  пуст — сервер генерирует. Новый код одноразовый, TTL 10 минут, прежние
  неиспользованные коды пользователя отзываются.
  Ответ: `{"code": "XXXX-XXXX-XXXX", "expires_at": "…"}`.
- `POST /v1/account/transfer/claim` (без auth) — тело `{"code": "…"}`.
  По коду возвращает `{"vault": "<base64>"}` и помечает код использованным.
  Ошибки: 404 (не найден/истёк/использован), 429 (лимит попыток на IP).

Сервер не видит содержимое vault (это зашифрованный клиентом blob) и не хранит код
в открытом виде (только SHA-256). Очистка просроченных/использованных записей —
в `PurgeExpired` (вызывается периодической задачей).

## Клиентская часть (план)

Формат vault — JSON, зашифрованный AES-256-GCM. Ключ шифрования:
`PBKDF2-HMAC-SHA256(code, salt=соль, 210k итераций)` — код знает только владелец,
поэтому даже сервер не может расшифровать бэкап.

Содержимое vault (открытый текст до шифрования):
- все записи `EncryptedSharedPreferences` («umbra_secure»): ed25519-seed,
  x25519-приватный, registration_id, user_id, username, phone и т.д.;
- таблицы Room: `identity_keys`, `crypto_records` (Signal-сессии/prekeys/LocalVault),
  `messages` (история с `localBody` — AEAD-копией открытого текста и ссылками
  на медиа с ключами), `chats`, `contacts`;
- версия формата.

Восстановление на новом телефоне:
1. claim → vault → расшифровать;
2. записать значения в SecurePrefs, вставить строки Room в транзакции
   (схема та же, миграция не требуется);
3. обычный вход `challenge/verify` (уже с ключами);
4. запустить штатный реалтайм-цикл: он подтянет сообщения, пришедшие после
   момента бэкапа, а файлы будут скачиваться с сервера по мере открытия
   (ключи расшифровки уже в истории).

UI:
- Настройки → пункт «Перенести на другой телефон» (экран с кодом);
- экран авторизации → режим «У меня уже есть аккаунт» (ввод кода).

## Безопасность

- Сервер не получает приватные ключи и открытые тексты — только ciphertext vault.
- Код короткоживущий (10 мин), одноразовый, попытки ввода лимитируются по IP.
- Слабый код = слабая защита бэкапа: код из 12 символов алфавита base32 (~60 бит)
  достаточно стоек в связке с TTL и лимитом попыток.
- После переноса старый телефон лучше разлогинить (выход удаляет и кэш медиа).
