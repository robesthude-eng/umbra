# Модель угроз Umbra (0.20)

Документ фиксирует, от чего система защищает сейчас, от чего — нет, и какие решения приняты осознанно. Формулировки в README и SECURITY.md должны совпадать с этим файлом; при расхождении прав этот файл.

## 1. Активы

| Актив | Где живёт | Последствия компрометации |
| --- | --- | --- |
| Содержимое сообщений | устройства; сервер видит только `payload` | полная потеря конфиденциальности переписки |
| Метаданные (кто-кому-когда) | PostgreSQL на сервере | восстановим соцграф, временные паттерны |
| Номера телефонов | база (часть — хеши), Telegram-доставка OTP | деанонимизация участников |
| Сессионные токены | устройство; хеш в базе | захват аккаунта |
| Кейринг хранилища (`storage-keys.json`) | файл вне БД | чтение облачных блобов и бэкапов |
| Медиа-блобы | диск/S3 | доступ к вложениям (если есть ключи) |
| Инвайт-коды (0.19) | хеши в БД | чужая регистрация в закрытом контуре |
| `METRICS_TOKEN` (0.20) | environment сервиса | утечка обезличенной телеметрии (без переписки) |

## 2. Модели противника

**A. Пассивный сетевой наблюдатель** (провайдер, Wi-Fi, DPI).
Защита: TLS через Caddy, прикладное шифрование тела сообщений. НЕ защищаем: факт использования сервера, размеры и тайминги пакетов, факт звонка (WebRTC/TURN).

**B. Компрометация сервера (root или доступ к БД).**
Защита: сервер не знает открытого текста сообщений; токены и коды OTP хранятся хешами; кейринг — вне БД.
НЕ защищаем: метаданные, доставка будущих сообщений (активный сервер может подменить прекеи — без верификации отпечатков это незаметно).

**C. Доступ к разблокированному устройству.**
Защита: список сессий и отзыв, удаление аккаунта с отдельным подтверждением. НЕ защищаем: локальная база Room не шифруется отдельным паролем — опора на шифрование Android и блокировку экрана.

**D. Нежелательный новый пользователь.**
Защита: `AUTH_ALLOWED_PHONES`, инвайт-коды (0.19), OTP-бюджеты и кулдауны, лимит числа номеров в окне.

**E. Злоупотребление ресурсами (DoS, забивание хранилища).**
Защита: `newRequestLimiter`, лимиты размера сообщений/медиа, квота на пользователя, `cmd/gc` для сиротских блобов, метрики 0.20 для раннего обнаружения.

## 3. Чего система СОЗНАТЕЛЬНО не делает

1. **Не скрывает метаданные.** Сервер видит пары отправитель-получатель и времена. Цена сокрытия (миксинг, заполнительный трафик) не соответствует сценарию малой закрытой группы.
2. **Не защищает от злонамеренного сервера без сверки отпечатков.** Сверка ключей вручную — ответственность пользователей (кандидат в будущие версии: UI сравнения safety number).
3. **Не скрывает факт звонка.** WebRTC/TURN раскрывает время и длительность.
4. **Не даёт forward secrecy для облачных копий.** Бэкапы шифруются долгоживущим кейрингом: утечка ключа открывает все сохранённые копии.
5. **Не защищает от компрометации Telegram-канала доставки OTP.** Кто видит чат с кодами — может войти в аккаунт. Компенсации: короткие TTL (5 мин), лимит попыток, привязка кода к запросу, уведомление о новой сессии.
6. **Не скрывает номер владельца от владельца сервера.** Модель доверия: сервер держит тот, кому доверяют участники.

## 4. Границы доверия

```
устройство (доверенное: ключи, открытый текст)
   | TLS
прокси Caddy (видит IP, пути, размеры)
   |
umbra-server (видит метаданные и шифротексты)
   |-- PostgreSQL (метаданные, хеши, payload)
   |-- blobstore / S3 (шифрованные вложения)
   |-- storage-keys.json (вне БД, владелец)
   |-- Telegram Bot API (канал доставки OTP) <- слабое звено
   |-- FCM (только сигнал «есть событие», без текста)
   |-- /metrics (обезличенные счётчики, отдельный токен)
```

Правило для нового кода: в логи, пуши и метрики не попадают номера, имена, тела сообщений и токены. Если нужна разбивка по сущностям — только хеши или схлопнутые категории.

## 5. Остаточные риски и что их закроет

| Риск | Сейчас | Что закроет |
| --- | --- | --- |
| Подмена ключей сервером | не детектируется | UI сверки отпечатков + уведомление о смене ключа |
| Локальная БД на устройстве | без своего шифрования | SQLCipher / ключ в Keystore + блокировка приложения |
| Кейринг рядом с бэкапами | один диск = одна точка отказа | вынос копии на отдельный носитель (docs/deploy.md) |
| OTP через Telegram | канал вне контроля | собственный релей + второй фактор при входе с нового устройства |
| Нет алертов на аномалии | есть базовые метрики (0.20) | правила Prometheus + уведомления владельцу |
| Нет проверки восстановления | есть `scripts/verify-restore.sh` (0.20) | запуск по таймеру раз в месяц |

## 6. Как обновлять этот документ

Любое изменение, которое добавляет новый внешний канал (пуши, аналитика, релеи, хранилища) или новый вид данных на сервере, обязано обновлять разделы 1, 4 и 5 в том же PR.
